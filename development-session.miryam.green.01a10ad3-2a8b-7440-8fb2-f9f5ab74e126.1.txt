A remote model for rare, one-shot work is a small feature. The costly part is deciding what single prompt to send. The local router should stay the only thing that runs on ordinary turns.

**How it would work.** Leave `REMOTE_URL` and a key file empty by default. Call it only when you ask, for example `python3 scripts/agent.py --remote "…"`, or when you name that step in the task. That call is one non-streaming completion: one assembled prompt, no tools, no transcript. The reply comes back as a single message, and the local coder applies it. A timeout and a size cap stop a hung remote call from stalling the loop. Off loopback the URL has to be `https`. `scripts/agent.py` already refuses to send an API key over plain `http` except to `127.0.0.1`, `localhost`, and `::1`.

**What would make it expensive.** If the remote model also runs tools, or receives the local history on every step, the wire traffic is the same bloat you want to avoid. The packer has to send the task plus the few files that matter. An automatic "this looks hard" classifier is a separate choice and should stay off.

`scripts/agent.py` already notices a stuck coder. The same tool call in the same epoch is skipped, and after two skips the next step is forced to stop calling tools and print a one-line summary. When one of those fires, and a remote login is configured, the agent stops the local loop and sends one request to the attached remote session. The brief is the original task, the paths touched, the last distinct tool result, and the call that got stuck. The remote reply is printed and saved on that session. It is not fed back into another automatic remote call. With no login configured, the agent prints that it is stuck and stops.

The remote context lives in named sessions under named logins. A login is a base URL, a model name, and a key file under `.secrets/remote/`. A session is a conversation on that login. The local file remembers the active login, the active session, and the remote conversation id when the provider has one. When it does not, the session stores only its own briefs and replies, and those are what the next call resends. Local tool chatter never enters that record. Switching login or session is how you keep two powerful models, or two lines of work, from sharing a context.

Six commands, as the first word of an agent run:

- `/remote` shows the active login, session, and whether auto-handoff is armed.
- `/remote login <name>` attaches a credential profile.
- `/remote session <name>` attaches a session. Later escalations continue that conversation.
- `/remote new` starts a fresh session on the current login and leaves the old one in place.
- `/remote on` and `/remote off` arm or disarm the automatic handoff. Off still leaves `/remote take` available.
- `/remote take` sends the current task now. `/remote ask <text>` sends that text and does not run the local coder first.

Auto-handoff stays off until `/remote on`, and it runs at most once per local task. The agent is still a single run, so these are commands at launch. There is no chat prompt yet where you could type them mid-loop. I have not built this.
